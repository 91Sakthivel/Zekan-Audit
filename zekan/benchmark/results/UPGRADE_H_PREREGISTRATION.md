# Upgrade (H) pre-registration — the NEAR-BIJECTION structural check

## What this document is

This is written before any calibration run, before any implementation code, before the check exists in any runnable form. It records the method, the guard-to-be-calibrated, the conditions we agree in advance will count as falsification, and the limitations we already know we're accepting — all before we've seen a single calibration number. Same discipline as `UPGRADE1_PREREGISTRATION.md` and `TEST_B_PREREGISTRATION.md`'s addenda: write down what we predict and what would count as failure, then go find out, not the other way around. If calibration produces a result that doesn't match what's written here, we record that plainly; we don't quietly redefine the guard until it looks right.

## Motivation

Upgrade 1's `NEAR_CERTAIN_UNDECLARED_LEAK` catches a target-copy by asking "does a fitted model, scored on temporal folds, achieve near-perfect AUC on this one feature?" That question works — B-3's `readmitted` clears it at AUC 1.0000, every fold, both n — but it is answered indirectly: it is estimator-coupled (locked to histgb, re-measurement required if the default estimator ever changes), it requires actual model fits (the entire cost investigation in this directory exists because of that), and per `UPGRADE1_PREREGISTRATION.md`'s own registry classification it carries `confirmed=False` — a statistical flag, not a confirmed fact, because a model's score is an inference, not a measurement of the data itself.

(H) asks a different and stronger question, directly: do the feature's **values** nearly perfectly **partition** the target? Not "does a model separate the classes well using this feature," but "does knowing this feature's value tell you the label, as a fact about how the rows are arranged, independent of any estimator." This is the same class of check as the existing `FORBIDDEN_ENTITY_LEVEL_AGGREGATE` (`zekan/detectors/schema.py:81,188`: `SourceLayer.DETECTED_STRUCTURAL`, `EvidenceScope.DATA_ONLY`, `confirmed=True`) — deterministic, no estimator, no RNG, no threshold derived from a fitted model's behavior. It earns `confirmed=True` because the finding is a fact about the data's own structure, not an inference drawn from how well a classifier happened to fit it.

(H) is not a replacement for Upgrade 1's screen. It is a second, independent instrument aimed at the same B-3-shaped blind spot, answering a related but distinct question by a completely different method — see "Scope honesty," below.

## Method, locked before calibration

### Signal: normalized conditional entropy (the uncertainty coefficient, Theil's U)

For every non-forbidden feature `X` and the binary target `Y`:

```
H(Y)     = -sum_y p(y) * log p(y)                         (marginal entropy of the target)
H(Y|X)   = sum_x p(x) * H(Y|X=x)
         = sum_x p(x) * [ -sum_y p(y|x) * log p(y|x) ]     (weighted average conditional entropy)
U        = (H(Y) - H(Y|X)) / H(Y)
```

`U` ranges from 0 (the feature's value tells you nothing beyond the base rate) to 1 (the feature's value determines the label exactly, with zero remaining uncertainty). The log base is irrelevant — it cancels in the ratio — so this is computed by counting a value/label joint frequency table, nothing else.

**Why this, and not raw purity.** Test B's target is imbalanced: 11,357 of 101,766 rows positive, an **11.16%** base rate (confirmed against the B-2 100k contract's own pre-flight output: `minority is 11.2%`, `{0: 90409, 1: 11357}` — 11,357/101,766 = 0.1116). A feature that maps **every row to the majority class**, carrying no information whatsoever, is **88.84% "pure" for free** — a number that reads as deceptively strong in isolation and would pass a naive fixed-purity threshold at almost any reasonable cutoff. Conditional entropy does not have this failure mode: a constant (or Y-independent) feature has `H(Y|X=x) = H(Y)` for its only value (or, more generally, `H(Y|X) = H(Y)` when `X` and `Y` are independent), giving `U = 0` **exactly** — the metric is defined relative to the base rate it must beat, not an absolute count of correct-looking rows. This is the direct structural analogue of why Upgrade 1 rejected a raw fixed-AUC cutoff in favor of a criterion that accounts for what "informative" actually means against the specific class balance in play.

### Deterministic, computed by counting — no model, no folds (in the fitting sense), no RNG

This is not something that needs `n_permutations`, a `model_factory`, or a `null_seed`. It is a joint frequency count over `(X, Y)` pairs, same computational family as `FORBIDDEN_ENTITY_LEVEL_AGGREGATE`'s constant-within-entity check.

**Whole-frame, not per-temporal-fold** — stated and justified now, not deferred to calibration:

Upgrade 1's screen is computed on temporal folds specifically to protect against **train/test asymmetry**: a model fit on rows before a boundary and scored on rows after it is the only way to know whether a feature's apparent signal would actually have been available at prediction time, rather than an artifact of fitting and scoring the same distribution. Conditional entropy has no analogous risk to protect against. It does not "fit" a model that could memorize idiosyncrasies of a training split and then be evaluated for whether that memorization generalizes — it directly characterizes the joint distribution of `(X, Y)` **as it exists in the given data**, with no claim about future or held-out rows. There is nothing to overfit to, because there is no held-out set being predicted. Computing it on the whole frame is therefore not a shortcut relative to a "more correct" per-fold version — it is definitionally what the statistic is asking about the dataset as given, and per-fold computation would answer a different (and here, unneeded) question about temporal stability.

**However** — and this is the reason "whole-frame" is not simply "safe by default" — the task's own framing names the real risk correctly: **a value that happens to appear in only one narrow slice of the data (e.g. one time period, or a handful of rows anywhere) can produce a spurious partition with no genuine dependency behind it.** This is not a train/test problem; it is a **support** problem, and it is the same underlying mechanism as the ID trap, below, just at a smaller scale. Splitting into folds would not fix this — it would make it **worse**, by fragmenting an already-thin per-value row count into even thinner per-fold-per-value counts, directly increasing the number of accidentally-single-occupancy values a fold could see. The correct defense against this is a minimum-support guard applied to the whole-frame computation (see below), not a fold split. Whether **per-period value locality** specifically (a value with adequate *total* support that is nonetheless concentrated entirely within one narrow time window) deserves its own separate check, distinct from a flat minimum-support floor, is an open question this pre-registration does not resolve — it is flagged here for calibration to examine, not answered in advance.

## The ID trap — the primary falsification risk

A feature that is **unique on every row** trivially achieves `U = 1.0`: each distinct value maps to exactly one row, hence to exactly one label, by construction — with zero information about whether the feature has anything to do with the target. Diabetes-130's `encounter_id` is exactly this case (verified directly: 10,008 distinct values on the 10,008-row `scratch/testB2_strat.csv` sample, i.e. unique on every row at 10k already, consistent with Zekan's own pre-flight note calling it ID-like), and **any** sufficiently fine-grained continuous-valued column shares the same property — this is not specific to an obviously-named ID column.

**The guard, shape only — numbers come from calibration:**

1. **A cardinality ceiling relative to row count.** A feature whose distinct-value count, as a fraction of total rows, exceeds some ceiling cannot be claimed to "partition" the target in any meaningful sense — a near-bijective mapping structurally requires cardinality approaching the row count. This is a cheap, up-front check, the same shape as Upgrade 1's own screenability gate (`undeclared_feature_probe.py`'s `_screenability_reason`) — filter before doing real work, report the exclusion, never silently drop it.
2. **A minimum support requirement per distinct value.** This is not redundant with (1) — it fixes the actual mathematical mechanism that inflates `U`: for any distinct value `x` with count `n_x = 1`, `H(Y|X=x) = 0` **trivially** (a single row has no internal disagreement to be uncertain about), so every singleton value directly pulls the weighted-average `H(Y|X)` toward 0 regardless of whether `X` and `Y` have any real relationship. A feature could pass a cardinality-ceiling check (moderate distinct-value count relative to rows) while still having a long tail of rare values that individually inflate `U` for reasons having nothing to do with genuine dependency. The fix is a floor on `n_x` — values below it are pooled into an aggregate "rare" bucket or excluded from the computation entirely, so no value's own accidental smallness can count toward the near-bijection claim.

Both guard components are pre-registered as required; **their combination and the specific thresholds are calibration's job**, not fixed here.

**`encounter_id` must not trigger. This is a named falsification condition, not a soft expectation**: if the calibrated guard — whatever shape it ends up taking — would still flag `encounter_id`, that is a **design failure to report**, exactly as `UPGRADE1_PREREGISTRATION.md` pre-committed for its own `number_inpatient` anchor. It is not a guard to quietly retune until `encounter_id` stops firing.

## Calibration plan (what will be measured, stated before measuring)

- **Score every non-forbidden feature** in the B-2 and B-3 frames (same frames, same row-count conditions `UPGRADE1_CALIBRATION.md` already used, so results are directly comparable to that document's own AUC-based distribution).
- **Named anchors, pre-committed as falsification conditions, not as targets to hit:**
  1. Raw `readmitted` **must** trigger. `readmitted_lt30` is derived directly from it, so it should determine the target exactly (`U` at or extremely near 1.0) — the direct structural analogue of Upgrade 1's own `readmitted` AUC-anchor requirement, this time as a fact about value/label correspondence rather than a model score.
  2. `encounter_id` **must not** trigger — the ID trap, restated as a calibration gate: if it fires, the guard as calibrated is wrong and that is reported as a failure, not adjusted after the fact to make this specific case pass.
  3. `number_inpatient` **must not** trigger — the same standing specificity anchor `UPGRADE1_PREREGISTRATION.md` used for its own SUSPECTED/NEAR_CERTAIN calibration, carried over here for a second, independent instrument to fail the same way if it's going to fail at all.
- **The threshold is set against the honest distribution's tail, and the margin is the evidence** — same discipline as Upgrade 1's own calibration plan. Report the **full `U` distribution** across every scored feature, and the **gap** between the honest tail's maximum and the leak anchor's value, explicitly, not just a final guard number. **If the honest distribution and the leak overlap — no clean separating gap — that is a finding to record and STOP on**, not a boundary to split arbitrarily inside an ambiguous region.
- **Cardinality interaction, specifically for `diag_1`/`diag_2`/`diag_3`.** These carry meaningfully higher cardinality than most of the frame — 700+ distinct ICD-9-style diagnosis codes reported over the full 101,766-row B-2/B-3 frames (consistent, directionally, with 445–468 distinct values already observed on the 10,008-row stratified sample — cardinality growing with more rows sampled from the same code space is expected and was not further re-derived here, per this task's read-only, no-audit scope). At an average of roughly 101,766 / 700 ≈ 145 rows per code, but with diagnosis-code frequency almost certainly power-law distributed in practice (a handful of common diagnoses, a long tail of rare ones) rather than uniform, these three columns sit exactly at the ambiguous middle the guard has to get right: genuinely too coarse-grained to be ID-like in aggregate, yet very likely containing individual rare codes with support thin enough to trip the per-value floor on their own. Calibration must report **how `diag_1`/`diag_2`/`diag_3`'s measured `U` is affected by their rare-code tail**, and **whether the guard's per-value pooling/exclusion correctly separates their real, moderate, well-supported categorical signal from any spurious inflation contributed by their rarest codes** — this is a harder, more informative test of the guard's correctness than the two-anchor extremes (`encounter_id` fully unique vs. `number_inpatient` low-cardinality) can provide on their own.

## Validation conditions (pre-registered)

- **B-3:** raw `readmitted` flagged by (H) with `confirmed=True`, **alongside** the existing `NEAR_CERTAIN_UNDECLARED_LEAK` annotation Upgrade 1 already produces for the same feature on the same frame. **These are two different kinds of evidence for the same conclusion — a deterministic structural fact (this feature's values partition the target) and a statistical-model fact (this feature's univariate AUC is near-perfect) — not two independent problems, and the surface must not present them as such.** The two blocks must not restate each other's claim in near-identical wording (no redundant "this predicts the target almost perfectly" language duplicated verbatim in both places), and when both fire on the same feature the rendering must make the connection explicit — an obvious cross-reference (e.g. "also flagged structurally below/above") rather than two unlinked warnings a reader could mistake for either a duplicate bug or two unrelated issues. Given `confirmed=True` is definitionally a stronger claim than `confirmed=False` (a fact about the data vs. a statistical inference from a model), (H)'s finding should be presented with at least equal prominence to `NEAR_CERTAIN`'s, not folded underneath it as a footnote. Exact rendering position/wording is a surfacing-step decision (not this task, which is pre-registration only), but the **no-redundancy, explicit-cross-reference requirement** is recorded here as a validation condition this design must satisfy.
- **B-1 and B-2:** no honest feature flagged. `encounter_id` not flagged in **any** of the three frames (B-1, B-2, B-3) — restated here as a cross-frame validation condition, not just a single-frame calibration gate.
- **Verdicts unchanged in all three.** (H) is annotate-only, like every structural probe that exists today (`FORBIDDEN_ENTITY_LEVEL_AGGREGATE`, `CORRELATED_LEAK_PAIR`, `ENTITY_CONTAMINATION`/`ENTITY_CONTAMINATION_RISK`, `TEMPORAL_LEAKAGE`, and Upgrade 1's own `NEAR_CERTAIN_UNDECLARED_LEAK`) — it never alters `policy_decision.verdict`. This is now an established design invariant across every one of Zekan's structural checks, not a new decision being made for (H) specifically.

## Scope honesty (accepted limitations, documented now, not built around later)

- **Does not catch a leak that is strongly but not deterministically related to the target.** A feature with real, substantial, but imperfect predictive power (the honest B-2 tail Upgrade 1 already measured — `number_inpatient` at AUC 0.6079, well short of a near-bijection) will not trigger (H), by design — that is exactly Upgrade 1's `NEAR_CERTAIN`/panel's job, not this check's. The two are deliberately complementary, not redundant with each other, and catching the same true leak with both instruments (as B-3's `readmitted` is expected to) is a **feature** — independent corroboration by two unrelated methods — not duplication to be pruned down to one.
- **Continuous leaks without repeating values are invisible to this check, and the ID-trap guard itself is the reason why.** A genuine, deterministic, bijective leak encoded as a high-cardinality or continuous value (e.g. a raw floating-point copy of a related continuous signal, with few or no repeated values across rows) would have cardinality indistinguishable from an identifier's — the same cardinality ceiling that correctly suppresses `encounter_id` would also suppress a real leak shaped like this. This is a genuine, acknowledged blind spot introduced by the guard that makes the check safe against false positives, not a gap to be silently patched here — recorded plainly, the same way `UPGRADE1_PREREGISTRATION.md` recorded its own univariate-only limitation.
- **Multivariate combinations are out of scope.** Two individually-innocent columns that jointly, but not individually, partition the target will pass clean — the same acknowledged gap `UPGRADE1_PREREGISTRATION.md` already recorded for its own univariate screen. Neither instrument, alone or together, is a combination-leakage detector.
- **Threat model is accidental leakage**, not an adversarial one — a value-to-label mapping check is at least as easy to defeat deliberately (any binning, hashing, or added noise breaks a clean partition) as Upgrade 1's AUC screen already acknowledged for itself.

## What still counts as success

Unchanged from the standard `UPGRADE1_PREREGISTRATION.md` already held itself to, and `TEST_B_PREREGISTRATION.md` before it: success is learning the true behavior of this design against real evidence, written down honestly whichever way it goes — not a calibration run massaged until every named anchor lands where we hoped. If `encounter_id` gets flagged, if `diag_1`'s rare-code tail defeats the per-value guard, if the honest and leak distributions overlap — every one of those is a valid, complete result for this pre-registration, to be reported exactly as it happens, not explained away.
